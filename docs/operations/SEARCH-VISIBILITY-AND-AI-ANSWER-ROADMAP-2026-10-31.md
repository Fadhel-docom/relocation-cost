# خارطة طريق الظهور والنمو العضوي — Relocation Cost
**الإصدار:** 1.0  
**تاريخ الاعتماد التخطيطي:** 2026-10-31  
**الحالة:** خارطة طريق تشغيلية مشتركة لـChatGPT وClaude؛ ليست ادعاءً بأن الأعمال نُفذت.  
**الهدف التجاري:** الوصول إلى أول تحويل/سحب قابل للتحقق، ثم بناء مسار نمو مستدام. لا ضمان لترتيب أو زيارات أو دخل.

## الرؤية: ثلاث طبقات مترابطة
1. **Google وBing:** جعل الصفحات المفيدة قابلة للاكتشاف والزحف والفهرسة، ثم تحسين ظهورها ونقراتها على استعلامات ذات نية واضحة.
2. **أصل بيانات قابل للاستشهاد:** دراسة أصلية عن تكاليف الانتقال بين مسارات أمريكية، ببيانات قابلة للتحقق ومنهجية منشورة؛ تُطلق فقط إذا كانت العينة والجودة والحقوق كافية.
3. **أداة قابلة للمشاركة والتضمين:** إصدار قابل للتضمين عندما يثبت طلب حقيقي من ناشرين/مواقع موارد، لا لمجرد بناء روابط.
4. **محركات الإجابة بالذكاء الاصطناعي:** معلومات دقيقة، منظمة، واضحة المصدر والحدود، بحيث تكون مؤهلة للاستخراج والاستشهاد عندما ترى المحركات أنها مفيدة. لا توجد حيلة أو علامة خاصة تضمن الظهور.

## مبادئ لا تُخرق
- قانون «القيمة قبل النشر» وملف `docs/value-before-publishing.md` يحكمان كل مرحلة.
- لا صفحات كثيرة لمجرد الكلمات المفتاحية، ولا تدوير صفحات الولايات/المسارات، ولا محتوى مولّد واسع النطاق.
- لا أرقام تكلفة أو نسب أو متوسطات غير موثقة، ولا نخلط بين سعر معلن من شركة نقل وتكلفة فعلية شاملة.
- نفرّق بين الاكتشاف والزحف والفهرسة والترتيب والنقر والزيارة والتحويل.
- لا تغيير لمعادلة الحاسبة أو مصدر المسافة أو معاملات الأسعار ضمن هذه الخطة دون بوابة دقة مستقلة؛ قرار المسافة/مزود Routing منفصل، ومراجعة الترخيص قائمة.
- لا شراء روابط، ولا رسائل جماعية، ولا نشر آلي في المجتمعات، ولا مراجعات مزيفة.
- لا نعد بأن إضافة Schema أو FAQ أو ملف AI خاص سيجعلنا نُعرض في الإجابات. الأساس محتوى مفيد قابل للفهم والزحف ومسنود بمصادر.
- كل نتيجة تُسجل مع التاريخ والنافذة ومصدر القياس، وتُقارن بنافذة مماثلة.

## خارطة التنفيذ ومراحلها

### المرحلة 0 — القياس والحقيقة التشغيلية (الأولوية الفورية)
**الهدف:** إنشاء لوحة حقيقة قبل تعديل المحتوى.
- حفظ قراءة GSC حسب الصفحة والاستعلام والجهاز والبلد، مع clicks/impressions/CTR/position، ونافذة 28 يومًا.
- قراءة Bing Search Performance وURL inspection وSitemaps/Crawl diagnostics؛ توثيق ما هو مؤكد وما هو غير حاسم.
- مصالحة اختلاف 109 مقابل 138 ظهورًا: خاصية التقرير، نوع التجميع، التاريخ، الفلاتر، وتأخر البيانات.
- استخراج قائمة URLs من sitemap الفعلي ومقارنتها بعينات GSC/Bing.
- تفعيل/التحقق من قياس الاستخدام المتاح في Vercel Analytics: صفحات الدخول، المصادر، الزيارات، أحداث بدء الحاسبة وإكمالها وCTA إن كانت الإمكانية متاحة. لا نضيف GA4 أو أداة مدفوعة تلقائيًا.
**مخرجات القبول:** baseline مؤرخ + جدول URL status + قائمة قياس conversion + عوائق واضحة.

### المرحلة 1 — اكتشاف وفهرسة Google وBing
**الهدف:** معالجة الأسباب لا إرسال طلبات عشوائية.
- لكل صفحة أولوية: تحقق من HTTP 200، عدم وجود noindex، robots، canonical ذاتي صحيح، وجودها في sitemap، HTML قابل للقراءة دون الاعتماد على تفاعل JS، وروابط داخلية قابلة للزحف.
- ابدأ بـhomepage و`/calculator/` و`/guides/moving-cost/` و`/guides/employer-relocation-package/` ثم صفحات المسارات الموجودة ذات القيمة.
- تحقق من سلسلة التحويلات والنسخة الأساسية (www/non-www، slash) وعدم وجود تكرار أو صفحات يتيمة.
- أصلح أي خلل مؤكد في PR منفصل واختبارات؛ بعدها فقط أعد إرسال sitemap أو اطلب فحص URL مرة واحدة عند استيفاء الشروط.
- Bing: تحقق من sitemap وIndexNow إن كان ملائمًا ومتاحًا، والروابط الداخلية وجودة الصفحات؛ لا تُكرر إرسال URL دون تغيير أو سبب.
**مخرجات القبول:** مصفوفة URLs فيها حالة منفصلة: مكتشف، مزحف، مفهرس، مستبعد/سبب، أو غير معروف؛ ولا ادعاء بفهرسة قبل تحقق الأدوات.

### المرحلة 2 — خريطة الكلمات المفتاحية ونية البحث
**الهدف:** ربط كل نية بصفحة واحدة مناسبة بدل تشتيت الكلمات.
- الرئيسية: moving cost calculator / US moving cost calculator ونية استخدام الأداة.
- صفحة الحاسبة: moving cost calculator by state / moving budget calculator، مع وصف واضح للمدخلات والمخرجات والحدود.
- دليل moving cost: how to calculate moving costs / what affects moving costs، مع إجابة عملية ومصادر.
- دليل employer relocation: employer relocation package / relocation allowance / relocation lump sum؛ لا ندّعي حساب الضرائب أو gross-up لأن المنتج لا يفعل ذلك.
- صفحات المسارات الموجودة: cost to move from [state] to [state] فقط حيث توجد بيانات فريدة قابلة للتحقق وتجربة مفيدة.
- لكل استعلام: نية المستخدم، الصفحة المستهدفة، دليل GSC أو بحث SERP، منافسون موثقون، فجوة المحتوى، قرار (تحسين/دمج/عدم إنشاء).
- لا نُنشئ صفحة جديدة قبل إثبات عدم وجود صفحة قائمة تلبي النية.
**مخرجات القبول:** keyword-to-page map مع منع cannibalization وقائمة أولويات لا تتجاوز القدرة على الجودة.

### المرحلة 3 — تحسين الصفحة وتجربة النقر (CTR)
**الهدف:** تحسين الوضوح والملاءمة دون clickbait.
- تحسين عنوان الصفحة وH1 والفقرة الأولى بحيث تذكر الحاجة الحقيقية وتشرح المنتج وحدوده.
- إظهار الحاسبة بوضوح على الرئيسية، ودراسة موضعها وتجربتها بعد حل اكتشاف `/calculator/`؛ لا نغيّر الرئيسية عشوائيًا لأنها الصفحة ذات أغلب الظهورات.
- إجابة قصيرة مباشرة على السؤال الذي تستهدفه الصفحة، ثم التفاصيل والمنهجية والمصادر.
- عناوين ووصف فريدان ودقيقان لكل صفحة؛ الوصف ليس ضمانًا أن Google سيستخدمه كما هو.
- تحسين الروابط الداخلية: روابط سياقية بين الرئيسية والحاسبة والأدلة والمسارات، ونص رابط يصف الوجهة طبيعيًا.
- تجربة الجوال: ظهور الإجابة/القيمة وCTA مبكرًا، جدول المسارات قابل للاستخدام دون قصّ مربك، وترتيب بصري واضح.
- قياس CTR حسب الصفحة والاستعلام مع مراعاة متوسط الموضع وحجم العينة؛ لا ننسب التغير لتعديل واحد دون دليل.
**مخرجات القبول:** PR صغيرة مع screenshots/اختبارات، وbaseline قبل/بعد بنفس النافذة.

### المرحلة 4 — محتوى يكتسب ثقة وروابط طبيعية
**الهدف:** تغطية احتياجات المستخدمين التي لا تجيب عنها المنافسة جيدًا.
- تحديث الأدلة القائمة بدل نشر مقالات متشابهة؛ لكل دليل: جواب، قائمة تكاليف شاملة، ما يشمله التقدير وما لا يشمله، مصادر وتاريخ تحقق، مثال موثق إن توفر.
- توضيح الفروق بين DIY وrental truck + labor وfull-service، وتجنب المقارنة الرقمية غير المتكافئة.
- بناء صفحة منهجية مفهومة تشرح مصادر البيانات، تاريخها، طريقة الحساب، الافتراضات، حدود الدقة، وما لا تحسبه الأداة.
- إدراج أمثلة عملية لمسارات محددة فقط إذا أمكن إعادة إنتاج الحساب والتحقق من المدخلات والمصادر.
- مراجعة المحتوى دوريًا عند تغير المصدر؛ لا نضع تاريخ تحديث شكليًا دون إعادة تحقق.
**مخرجات القبول:** صفحات قليلة لكنها مفيدة، موثقة، ومختلفة فعليًا عن الصفحات المنافسة.

### المرحلة 5 — أصل بيانات قابل للاستشهاد (Research Asset)
**الهدف:** دراسة أصلية عن تكاليف الانتقال بين المسارات الأمريكية قد تستخدمها مواقع الموارد والصحافة والباحثون.
**بوابة الجدوى قبل الجمع:**
- تعريف السؤال بدقة: كيف تختلف تقديرات النقل حسب المسافة وحجم المنزل ونوع الخدمة؟ لا ندّعي تمثيل متوسط السوق إذا كانت البيانات أسعارًا منشورة محدودة.
- تحديد مجتمع الدراسة والعينة والمسارات ومعايير اختيارها، وفترة جمع البيانات.
- تحديد مصادر قابلة للتحقق ومسموح باستخدامها: بيانات عامة/أولية، أسعار منشورة مع شروطها، عروض أسعار حقيقية بموافقة أصحابها مع إزالة المعلومات الشخصية، أو بيانات حكومية مناسبة.
- فصل السعر المعلن عن العرض الفعلي، وفصل truck rental عن labor وعن full-service؛ لا نجمعها في رقم واحد مضلل.
- نشر قاموس بيانات ومنهجية وتاريخ snapshot وقواعد الاستبعاد والتحويل والوحدات والقيود، مع روابط المصدر لكل قيمة.
- اختبار إمكانية إعادة إنتاج النتائج من ملف بيانات نظيف؛ إظهار حجم العينة وتوزيعها وعدم اليقين.
- مراجعة حقوق الاستخدام والتراخيص وشروط التخزين والإسناد قبل إعادة نشر أي بيانات.
**التنفيذ عند اجتياز البوابة:**
1. تصميم مخطط البيانات ومصدر كل حقل.
2. جمع عينة تجريبية صغيرة واختبار الجودة.
3. تقييم التغطية والانحياز والفجوات؛ توسيع العينة فقط إذا أمكن.
4. تحليل المسارات/المسافات/أحجام المنازل/أنواع النقل دون ادعاء سببية.
5. مراجعة مستقلة للحسابات والمصادر.
6. نشر صفحة الدراسة + CSV قابل للتنزيل + المنهجية + تاريخ التحديث + ملخص الرسوم.
7. إعداد موجز اقتباسات ورسوم قابلة لإعادة الاستخدام مع رابط المصدر.
**بوابة النشر:** إذا لم تكن العينة كافية أو الحقوق غير واضحة أو لم تضف الدراسة معرفة جديدة، لا ننشرها كـ«دراسة وطنية»؛ نعيد صياغتها كتحليل محدود أو نوقفها.
**مؤشرات:** روابط مرجعية طبيعية ذات صلة، إحالات، تنزيلات، استشهادات موثقة، وليس عدد الروابط فقط.

### المرحلة 6 — توزيع الدراسة وبناء العلاقات
- إعداد قائمة صغيرة من مواقع موارد الانتقال والموارد الوظيفية والمالية والجامعات/مراكز البحث التي تناسب الدراسة فعلًا.
- لكل جهة: سبب ملاءمة محدد، صفحة مناسبة، محرر/سياسة إرسال، وصياغة شخصية غير مضللة.
- إعداد رسالتين تجريبيتين كحد أقصى؛ لا إرسال دون موافقة المالك إذا كان ذلك يتطلب تواصلًا خارجيًا.
- نشر الدراسة في صفحات المشروع وربطها داخليًا بالأداة والأدلة.
- متابعة الإحالات والروابط الجديدة في GSC وBing، مع فحص جودة المصدر وسياق الرابط.
- لا شراء روابط أو تبادل آلي أو حملات واسعة.
**مخرجات القبول:** أصل منشور قابل للتحقق + outreach محدود وذو صلة + تقرير النتائج.

### المرحلة 7 — أداة قابلة للمشاركة والتضمين
**لا يبدأ التطوير حتى يثبت الطلب.** إشارات الطلب المقبولة: طلبات تضمين حقيقية، إحالات من صفحات الموارد، استخدام متكرر/مشاركة من الزوار، أو ناشر مستعد لاختبارها.
- تحديد المهمة الوحيدة التي ستُضمّن: حاسبة تقدير مبسطة أم أداة كاملة؛ لا نكرر المنتج دون سبب.
- تجربة prototype محدودة مع ناشر/مستخدمين، وقياس بدء/إكمال الأداة.
- تصميم embed آمن ومستجيب مع attribution واضح باسم Relocation Cost ورابط عودة طبيعي، دون نصوص روابط محسّنة مصطنعة.
- عزل صفحة التضمين تقنيًا، واختبار CSP/iframe والأمان والوصولية والجوال، وتحديد سياسة الخصوصية والبيانات.
- منع تكرار المحتوى المفهرس: تحديد canonical/noindex وفق البنية المعتمدة قبل الإطلاق، وعدم جعل صفحة التضمين doorway.
- اختبار الأداء، التحميل، الأخطاء، الإصدارات، وتوثيق طريقة التضمين.
**بوابة النشر:** دليل طلب + فائدة للمضيف + تجربة ناجحة + مراجعة أمنية/SEO؛ وإلا تبقى الفكرة مؤجلة.

### المرحلة 8 — الظهور في محركات الإجابة بالذكاء الاصطناعي
**المبدأ:** الأهلية تأتي من محتوى موثوق ومفيد وقابل للاكتشاف؛ لا يوجد ضمان استشهاد ولا إعداد سحري.
- كتابة إجابات مباشرة ومحددة أعلى المحتوى، ثم دعمها بتفسير وأمثلة وحدود ومصادر أولية.
- توحيد المصطلحات والوحدات والتواريخ، وتعريف المقاييس (estimate, quote, rental, full-service) بوضوح.
- إظهار المؤلف/المراجع التحريري عند وجود مراجعة حقيقية، وتاريخ التحقق، ومنهجية الحساب، ومعلومات الاتصال/الهوية والسياسات بشفافية.
- ربط كل ادعاء رقمي بمصدر قابل للفتح، مع إظهار فترة المصدر وما إذا كان سعرًا معلنًا أو عرضًا.
- جعل المحتوى قابلاً للزحف والوصول في HTML؛ لا تحجب جوهر الإجابة خلف تفاعل أو تسجيل.
- استخدام structured data فقط عندما يطابق المحتوى المرئي والحقائق الفعلية؛ لا FAQ schema للتحايل ولا بيانات منظمة مختلقة.
- تحسين سمعة المصدر عبر الدراسة الأصلية والروابط التحريرية ذات الصلة، لا عبر تكرار الاسم أو صفحات مولدة.
- فحص عينة ثابتة من أسئلة المستخدمين في محركات الإجابة دوريًا، وتسجيل التاريخ والمحرك والسؤال والرابط/الاقتباس إن ظهر؛ النتائج شخصية ومتغيرة ولا تمثل قياسًا شاملاً.
- تطبيق SEO الأساسي وإرشادات Google/Bing؛ لا نحتاج صفحات أو ملفات خاصة لمجرد «AI SEO» إلا إذا وثقت محركات البحث متطلبًا رسميًا جديدًا.
**مخرجات القبول:** محتوى موثق، قابل للفهم والاقتباس، سجل رصد مؤرخ، وعدم ادعاء ظهور غير مثبت.

## توزيع العمل والتنسيق
**ChatGPT**
- يملك التحليل الاستراتيجي، قراءة GSC/Bing عند توفر الصلاحية، تشخيص الفهرسة، بحث الكلمات والـSERP والمنافسين، تصميم منهجية الدراسة وتدقيق المصادر، مراجعة ملاءمة فرص التوزيع، ومراجعة جودة ادعاءات AI-search.
- يكتب في OPS-ROOM وWORK-LOG ما قرأه وما أنجزه، ولا يكرر عمل Claude دون سبب.

**Claude**
- يراجع قاعدة الشيفرة والصفحات والقوالب، ينفذ تغييرات المحتوى/التقنية في فروع وPRs مستقلة، يضيف الاختبارات، يتحقق من العرض على الجوال، ويقترح أدوات القياس القابلة للتنفيذ.
- يراجع خارطة الطريق ويضيف اعتراضاته ومخاطر التنفيذ في WORK-LOG قبل أي تغيير متعارض.

**العمل المشترك**
- ChatGPT يحدد فرضية مدعومة وملفات النطاق، Claude يراجع التنفيذ أو يعترض بالأدلة؛ ثم مراجعة متبادلة قبل الدمج.
- مهمة واحدة ذات معنى لكل تسليم Claude، بحجم يناسب حصته المجانية.
- لا يدمج أي طرف PR للطرف الآخر دون مراجعة واضحة ونجاح CI.
- لا تزامن في تحرير الملف نفسه؛ يُسجل الفرع والملفات والمالك المسؤول.

## تعريف النجاح المرحلي
1. أول صفحة ذات أولوية يتم اكتشافها وفهرستها بعد تحقق موثق.
2. أول نقرة بحث عضوية موثقة.
3. نمو مستدام في النقرات والزيارات مع تحسن صفحات ذات نية واضحة.
4. أول استخدام مكتمل للحاسبة من زائر غير داخلي، ثم أول تحويل تجاري قابل للتحقق.
5. أول سحب فعلي؛ ثم تقييم هدف 3,000 دولار شهريًا بناءً على بيانات التحويل والاقتصاديات، لا التوقعات.
